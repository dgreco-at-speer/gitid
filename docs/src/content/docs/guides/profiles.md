---
title: Creating and managing profiles
description: Create, inspect, edit, and remove gitid profiles — interactively, with flags, or by hand-editing profiles.toml.
---

A **profile** is a named git identity: `user.name` and `user.email`, plus an
optional SSH key, commit-signing setup, isolated GitHub CLI auth, extra
environment variables, and raw git config passthrough. Profiles live in
`~/.config/gitid/profiles.toml`; everything derived from them (per-profile
gitconfig fragments, the includeIf manifest, gh config dirs) is generated by
gitid.

Once a profile exists, assign it to a directory tree with `gitid use` — see
[Directory mappings](../directory-mappings/).

## The interactive wizard

Run `gitid add` with no arguments (or just a name) in a terminal and gitid
walks you through everything:

```sh
gitid add
```

The wizard prompts for:

- **Profile name** — a lowercase slug (it becomes a filename, so it must match
  `^[a-z0-9][a-z0-9_-]*$`).
- **Git user.name** and **user.email**.
- **SSH key** — gitid discovers candidate private keys under `~/.ssh` by
  inspecting file *contents* (so a key named `work` is found just as well as
  `id_ed25519`), plus any paths referenced by `IdentityFile` directives in
  `~/.ssh/config`. Pick one from the list, enter a path manually, or choose
  none.
- **Commit signing** — none, `ssh`, or `openpgp`, then the key and whether to
  sign commits by default. If you picked an SSH key, its `.pub` sibling is
  offered as the default signing key.
- **GitHub CLI isolation** — whether to provision a separate `GH_CONFIG_DIR`
  so this profile gets its own `gh` login (default yes).

Any flags you pass alongside are used as defaults, so `gitid add work
--email jane@corp.example` pre-fills the email prompt.

:::note
The wizard requires a terminal. In scripts and automation, always pass
`--non-interactive` (see below) — otherwise `gitid add` will try to prompt and
block.
:::

## The flags form

Every field the wizard asks about has a flag:

```sh
gitid add <name> \
  --git-name "<user.name>" \
  --email <user.email> \
  --ssh-key <path-to-private-key> \
  --signing ssh|openpgp|none \
  --signing-key <pubkey-path-or-key-id> \
  --sign-commits \
  --gh | --no-gh \
  --non-interactive
```

With `--non-interactive`, gitid fails instead of prompting for anything
missing: `--git-name` and `--email` are required. GitHub CLI isolation is
**enabled by default**; pass `--no-gh` to opt out (`--gh` explicitly re-enables
it). When `--signing` is `ssh`, the signing key defaults to the profile's SSH
key `.pub`; when `openpgp`, a new GPG key is generated unless `--signing-key`
names an existing one.

### Example: a full "work" profile

SSH key, SSH commit signing, and isolated `gh` auth:

```sh
gitid add work --non-interactive \
  --git-name "Jane Doe" --email jane@corp.example \
  --ssh-key ~/.ssh/id_work \
  --signing ssh --signing-key ~/.ssh/id_work.pub --sign-commits
```

### Example: a minimal "personal" profile

Just a name and email, no gh isolation:

```sh
gitid add personal --non-interactive \
  --git-name "Jane" --email jane@home.example \
  --no-gh
```

Every mutating command (`add`, `edit`, `remove`, `use`, `forget`) runs a sync
automatically, so the generated files are always up to date afterwards. `gitid
add` also bootstraps the single `[include]` line in your global gitconfig on
first use.

## Listing and inspecting

```sh
gitid list                    # table; ● marks the profile active for your cwd
gitid list --format names     # one name per line (script-friendly)
gitid list --format json
```

`gitid ls` is an alias. To see one profile in full — including the path of its
generated gitconfig fragment and which directories map to it:

```sh
gitid show work
gitid show work --format json
```

## Editing a profile

`gitid edit` changes fields with the same flags as `add`, then syncs:

```sh
gitid edit work --email jane.doe@corp.example
gitid edit work --ssh-key ~/.ssh/id_work_new
gitid edit work --signing openpgp --signing-key ABCD1234
gitid edit work --signing none            # turn signing off entirely
```

When you switch the signing format, the existing signing key is kept if you
don't pass `--signing-key` (and setting signing for the first time requires
it).

:::caution
`gitid edit <name> --open` (open `profiles.toml` in `$EDITOR`, then sync) is
defined but **not implemented yet** — it currently errors and tells you to
edit the file directly and run `gitid sync`. Which brings us to:
:::

## Hand-editing profiles.toml

`~/.config/gitid/profiles.toml` is the source of truth and is meant to be
edited by hand — gitid preserves your formatting and comments. Some things
(per-profile env vars, raw git config passthrough, `tags = true` for tag
signing) can *only* be set here:

```toml
version = 1

[profiles.work]
name  = "Jane Doe"
email = "jane@corp.example"

[profiles.work.ssh]
key = "~/.ssh/id_work"

[profiles.work.signing]
format  = "ssh"
key     = "~/.ssh/id_work.pub"
commits = true
tags    = true

[profiles.work.env]
GLAB_CONFIG_DIR = "~/.config/glab-work"

[profiles.work.extra]
"url.git@github.com-work:.insteadOf" = "git@github.com:"
```

After any hand edit, regenerate the derived files:

```sh
gitid sync
```

See the [profiles.toml reference](../../reference/profiles-toml/) for the full
schema.

## Removing a profile

```sh
gitid remove personal         # alias: gitid rm
```

If any directories are mapped to the profile, `remove` refuses and lists them:

```console
$ gitid remove work
✗ 2 director(ies) are mapped to "work":
    /home/jane/code/work/
    /home/jane/code/clients/
error: refusing to remove a profile in use; pass --force to remove it and its mappings
```

`gitid remove work --force` (or `-f`) removes the profile **and drops those
mappings**. The profile's gh config dir
(`~/.local/share/gitid/gh/<name>/`) holds auth tokens and is never deleted —
gitid tells you where it is so you can delete it manually if you no longer
need it.
